# REST API Fundamentals

An API, or application programming interface, defines how software components communicate. A web API commonly exposes resources through URLs and transfers representations, often JSON, over HTTP. REST is an architectural style built around stateless interactions and resource representations, not a specific programming language or a requirement to return JSON. A resource might be a user, article, or order, identified by a path such as `/users/42`. A clear API uses consistent naming and behavior so clients can understand how to read or change those resources.

HTTP methods express the intent of a request. `GET` retrieves a representation and should not change server state. `POST` commonly creates a subordinate resource or triggers an operation. `PUT` replaces a resource representation and is generally idempotent: repeating the same request has the same intended effect. `PATCH` applies a partial update, while `DELETE` requests removal. Idempotency matters when clients retry requests after network failures. APIs should document any deviations or side effects rather than assuming that method names alone explain all behavior.

HTTP status codes tell clients how a request turned out. `200 OK` indicates success with a response, `201 Created` indicates successful creation, and `204 No Content` indicates success without a response body. `400 Bad Request` commonly signals invalid request data, `401 Unauthorized` means valid authentication is absent or failed, and `403 Forbidden` means the caller is not allowed to perform the action. `404 Not Found` indicates no matching resource, while `409 Conflict` can represent a conflict with current state. `500`-class responses signal server failures. An API should use status codes consistently and provide a stable, documented error body without leaking internal stack traces.

Request validation checks structure, types, required fields, and domain rules at the server boundary. Clients cannot be trusted to enforce these rules. Responses should have predictable shapes and include only fields the caller is allowed to see. Pagination is important for collection endpoints: page/limit or cursor-based parameters prevent unbounded responses. Cursor pagination can behave more consistently than offsets when rows are added during browsing, but it requires a stable sort key and a documented cursor model. Filtering and sorting parameters should be constrained to supported fields rather than interpolated into database queries.

Authentication establishes who a caller is; authorization determines what that caller may do. An authenticated identity is not automatically permitted to access every resource. Check access on each relevant operation, including whether a user may read or modify a specific record. Protect transport with HTTPS. Tokens, passwords, and other credentials should not be placed in URLs or logs. Apply rate limits and resource limits where appropriate, and treat uploaded or supplied data as untrusted. CORS controls which browser origins may make cross-origin requests; it is not authentication and does not protect an API from non-browser clients.

Good API design includes documentation of paths, methods, parameters, schemas, status codes, authentication, and examples. Versioning can help manage incompatible changes, but backward-compatible evolution is often preferable where practical. Tests should cover normal responses, invalid input, permission failures, and edge cases. Observability should capture useful request identifiers, durations, and error information while avoiding sensitive payloads. Clients and servers communicate across unreliable networks, so timeouts, retries, and duplicate requests need deliberate handling. A reliable API treats error semantics and operational limits as part of its contract.
