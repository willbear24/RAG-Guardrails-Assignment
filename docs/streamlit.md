# Streamlit

Streamlit is a Python framework for building interactive data applications with a script-oriented workflow. A developer writes a Python script containing layout commands and widgets; when a user interacts with a widget, Streamlit reruns the script from top to bottom. This rerun model makes small applications easy to create, but it changes how state and expensive computations should be managed. Code should be structured so that rerunning it is predictable and does not accidentally repeat costly or destructive operations.

Widgets such as `st.button`, `st.selectbox`, `st.text_input`, and `st.slider` provide inputs and return their current values during a run. A widget can have a key that identifies its state and lets the application refer to it consistently. `st.session_state` stores values across reruns for the current user's session, making it useful for chat history, intermediate choices, or workflow progress. It is not a database: state may not be durable across restarts or shared among users. Initialize state carefully and avoid assuming that a key exists before it has been set.

The `st` API provides layout and display elements, including titles, text, tables, charts, columns, tabs, sidebars, and expanders. Organize the page around the user's task, with a clear hierarchy and feedback after actions. For long-running operations, use a spinner or progress indicator and communicate errors in a visible, actionable way. Avoid exposing tracebacks, secrets, or raw internal data in the interface. Accessibility matters: use meaningful labels, maintain readable contrast, and do not communicate important states only through color.

Caching can improve responsiveness when work is repeatable. `st.cache_data` is intended for data computations whose results can be reused, while `st.cache_resource` is for shared resources such as a model or database connection pool. Cached values may outlive one script rerun and can be shared more broadly than session state, so consider whether data is user-specific or sensitive before caching it. Define cache keys and invalidation behavior thoughtfully. A function that depends on changing external state may return stale results unless its inputs or cache policy account for that change.

Forms batch multiple widget values so they are submitted together rather than triggering an action on every change. This is helpful when inputs should be validated as a group. File uploaders and user-controlled text should be treated as untrusted input, with limits on size and permitted formats. If the app connects to an external API, set timeouts and handle network failures explicitly. Keep credentials in Streamlit secrets or an appropriate deployment secret manager, not in code or public repositories.

Streamlit applications can be tested at different levels. Unit-test ordinary Python functions for transformations, validation, and business logic independently of the UI. Streamlit's testing support can exercise scripts and widgets, while deployed applications should also be checked for configuration and operational behavior. Separate reusable logic into modules instead of placing every operation in the page script. For larger projects, this makes database access, model calls, and error handling easier to test and maintain. Deployment requires the correct Python dependencies, configuration, and resource limits; local success alone does not guarantee that a cloud deployment has the same files or environment.
