# SQL Fundamentals

SQL, the Structured Query Language, is used to define, read, and change data in relational database systems. A relational database organizes information into tables made of rows and columns. A column has a data type, such as integer, text, date, or decimal, and a row represents one record. A primary key uniquely identifies a row. A foreign key refers to a key in another table and helps preserve relationships. Choosing suitable data types and constraints prevents invalid data from entering the database and communicates the intended meaning of fields.

The basic read operation is `SELECT`. A query lists the columns to return and a `FROM` clause identifies the source table. `WHERE` filters rows, `ORDER BY` sorts results, and `LIMIT` caps the number returned in systems that support that syntax. A filter should be explicit: without `ORDER BY`, row order is not guaranteed. Comparisons include equality and inequalities; `AND`, `OR`, and parentheses combine conditions. SQL has a special `NULL` value meaning missing or unknown, so test for it with `IS NULL` or `IS NOT NULL`, not `= NULL`. Comparisons involving NULL evaluate to unknown rather than true or false.

Aggregate functions summarize rows. `COUNT`, `SUM`, `AVG`, `MIN`, and `MAX` are common examples. `GROUP BY` divides rows into groups for aggregation, and `HAVING` filters groups after aggregation. `WHERE` filters individual rows before grouping. These clauses have distinct roles; using `WHERE` for a condition on an aggregate is not correct. A query with several aggregates should ensure each aggregate refers to the intended filtered set, especially when joins can duplicate rows.

Joins combine related tables. An inner join returns rows with matching values on both sides. A left join preserves every row from the left table and fills right-side columns with NULL when no match exists. Join conditions commonly compare a foreign key to a primary key. Missing or incorrect join conditions can create a Cartesian product, multiplying rows unexpectedly. Before trusting a result, check the expected number and uniqueness of rows. Database normalization separates facts into related tables to reduce duplication and update anomalies, while joins assemble information for reading.

Data changes use `INSERT`, `UPDATE`, and `DELETE`. An `UPDATE` or `DELETE` without a restrictive `WHERE` clause may affect every row, so confirm the intended filter and use transactions for important changes. A transaction groups statements so they can be committed together or rolled back. ACID describes key transaction properties: atomicity, consistency, isolation, and durability. The exact isolation levels and locking behavior depend on the database. Constraints, rather than only application checks, are important for preventing duplicate or invalid records under concurrent writes.

Indexes can speed up lookups and joins by helping the database find rows without scanning an entire table. They consume storage and add work to inserts, updates, and deletes, so adding indexes indiscriminately can make writes slower. Choose indexes based on common query patterns and verify with query plans and measurements. SQL injection occurs when untrusted input is treated as SQL syntax. Use parameterized queries or a well-designed query builder so data values remain separate from the SQL statement. Never rely on escaping strings by hand. Finally, avoid retrieving columns or rows that are not needed, and design pagination and query limits to keep application resource use predictable.
