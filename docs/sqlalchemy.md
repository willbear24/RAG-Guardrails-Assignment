# SQLAlchemy

SQLAlchemy is a Python toolkit for working with relational databases. It offers a Core layer for constructing SQL expressions and a higher-level ORM that maps Python classes to database tables. The ORM can make application code easier to organize, but it does not remove the need to understand SQL, transactions, indexes, constraints, and query cost. SQLAlchemy supports multiple database dialects; connection URLs and some capabilities vary by database driver. A project should choose and configure its driver intentionally, and credentials should be supplied through secure configuration rather than committed source code.

An `Engine` is the central object for database connectivity and connection pooling. It is usually created once for an application with `create_engine`. The engine does not mean that a connection is permanently open; it manages connections as work needs them. ORM mappings describe how classes correspond to tables. In modern SQLAlchemy, a declarative base and `Mapped` annotations can express mapped columns and relationships. A primary key identifies each row, while foreign keys express references between tables. Database constraints such as `NOT NULL`, `UNIQUE`, and `CHECK` protect important data rules even when writes come from more than one part of an application.

An ORM `Session` tracks objects and manages a unit of work. Changes to mapped objects are generally collected and sent to the database on flush or commit. A commit makes the transaction's changes durable according to the database's transaction behavior; a rollback cancels uncommitted work. Sessions should have a clear, short lifetime associated with a request, job, or other unit of work. They are not a global cache and should not be shared casually between concurrent tasks. Context managers and application framework dependency patterns can ensure sessions are closed even when errors occur.

Queries can retrieve rows, filter conditions, order results, limit output, and combine related tables. Relationship loading deserves attention. Lazy loading can issue extra queries when related attributes are accessed, sometimes creating the N+1 problem: one query fetches a list and another query runs for each item's relationship. Eager-loading strategies such as `selectinload` or `joinedload` can reduce round trips when their tradeoffs fit the result shape. Inspect emitted SQL and measure performance rather than assuming an ORM expression is efficient. For large tables, use pagination or streaming patterns and avoid loading unnecessary columns or entire datasets into memory.

Transactions group database operations so they succeed or fail as a logical unit. If a transaction raises an error, rollback before reusing the session. Database isolation, locking, and uniqueness constraints help handle concurrent updates; application-level checks alone can race when two requests act at once. When a database error occurs, do not silently convert it into a success-shaped result. Log useful context without exposing secrets, and return an appropriate application error.

Schema changes are normally managed with migrations, commonly using Alembic alongside SQLAlchemy. A migration records a deliberate change from one schema state to another and may include a reverse operation. `create_all` is useful for small experiments or tests, but it does not replace migration history for an evolving production database. Test migrations against representative database versions and plan data backfills and locks for large changes. Use bound parameters or SQLAlchemy expressions for values rather than concatenating untrusted text into SQL. ORM use does not automatically prevent every database security problem, especially when manually composing raw SQL.
